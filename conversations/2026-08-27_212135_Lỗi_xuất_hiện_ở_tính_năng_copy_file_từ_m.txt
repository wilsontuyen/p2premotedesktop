1. Windows Explorer sẽ gọi API `GetClipboardData` để lấy file và **bị block/chặn** lại ở đó để chờ dữ liệu.
2. Windows sẽ gửi message `WM_RENDERFORMAT` tới ứng dụng của chúng ta để yêu cầu tải dữ liệu thật.
3. Trong lúc xử lý `WM_RENDERFORMAT`, để xác định xem đây có phải là thao tác Paste thực sự hay không, code của chúng ta có gọi hàm `win32gui.GetWindowText(hwnd_fg)` để lấy tiêu đề cửa sổ hiện tại (mục đích là bỏ qua nếu đó là cửa sổ Remote Desktop).
4. Hàm `GetWindowText` của Windows hoạt động bằng cách gửi một message `WM_GETTEXT` tới cửa sổ Explorer (cửa sổ hiện tại) và đợi Explorer trả lời.
5. Tuy nhiên, luồng giao diện của Explorer lúc này đang bị **block** ở bước 1 để đợi ứng dụng chúng ta trả dữ liệu, do đó nó không thể trả lời message `WM_GETTEXT`.
=> Dẫn tới hiện tượng **Deadlock (treo chéo)**: Explorer đợi ứng dụng, ứng dụng đợi Explorer. Thế là dialog tải file của Windows bị đứng yên và file không bao giờ được tải. Timeout mặc định 5 giây của Windows sau đó sẽ đáăng và hủy toàn bộ thao tác. Ở lần Paste đầu tiên thường có một trick vượt rào giúp nó không bị mắc kẹt, nhưng từ lần thứ hai trở đi hoặc copy qua chuột phải chắc chắn sẽ dính.

**Cách khắc phục:**
Tôi đã sửa lại bằng cách thay thế hàm `win32gui.GetWindowText()` bằng hàm API `SendMessageTimeoutW` (với cờ `SMTO_ABORTIFHUNG`). Nhờ đó, nếu thấy Explorer đang bị treo/chờ, ứng dụng sẽ lập tức bỏ qua việc lấy tên cửa sổ mà tiếp tục chạy lệnh tải file ngay, phá vỡ được Deadlock.
